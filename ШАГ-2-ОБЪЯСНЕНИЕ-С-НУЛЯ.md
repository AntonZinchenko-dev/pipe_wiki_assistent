# Часть I. Что мы вообще построили

## 1. Задача

У компании есть вики — набор документов. Регламенты, описания сервисов,
разборы аварий. Сотрудник хочет спросить человеческим языком: «можно ли
выкладывать релиз в пятницу?» — и получить ответ со ссылкой на документ, а не
десять ссылок, которые надо читать самому.

## 2. Как это работает: аналогия с библиотекарем

Представь очень быстрого, но очень буквального библиотекаря.

Он не помнит содержание книг. Зато он умеет за секунду найти на полках те три
абзаца, которые похожи на твой вопрос, положить их перед собой и **прочитать
вслух ответ, глядя только в эти абзацы**. Ничего из головы он не добавляет —
ему запрещено.

Такая схема называется **RAG** — Retrieval-Augmented Generation, «генерация,
подкреплённая поиском». Два слова в названии — это два разных механизма:

- **Retrieval, поиск.** Найти нужные абзацы. Это не модель, это почти обычный
  поиск, просто умный.
- **Generation, генерация.** Языковая модель (у тебя это `qwen2.5:7b`,
  крутится локально через Ollama) читает найденные абзацы и формулирует ответ.

Зачем так сложно, почему не спросить модель напрямую? Потому что модель не
знает вашу вики — её учили на интернете. Спросишь напрямую — она придумает
правдоподобный ответ, и это худший из возможных исходов: по правдоподобному
ответу человек примет решение. Поэтому мы не спрашиваем модель «что ты
знаешь», мы даём ей текст и спрашиваем «что здесь написано».

## 3. Из чего состоит наш конвейер

Когда приходит вопрос, происходит шесть шагов.

**Шаг 1. Вопрос превращается в числа.** Есть отдельная модель (`bge-m3`),
которая превращает любой текст в список из 1024 чисел — это называется
**эмбеддинг** или «вектор».

Аналогия: представь, что каждому тексту мы присваиваем координаты в очень
многомерном городе. Тексты про близкие темы получают близкие адреса. «Можно ли
выкладывать в пятницу» и «регламент выкладки релизов» окажутся на соседних
улицах, даже если у них нет ни одного общего слова.

**Шаг 2. Ищем похожее двумя способами сразу.**

- *По векторам*: какие абзацы живут ближе всего к адресу вопроса. Ловит смысл,
  не требует совпадения слов.
- *По словам* (это называется BM25 — обычный полнотекстовый поиск): какие
  абзацы содержат те же слова. Ловит точные артикулы вроде `E-1042`, которые
  векторный поиск размазывает.

Оба нужны. Векторный найдёт «пятницу» в тексте про «конец недели», но
провалится на коде ошибки. Словесный найдёт код ошибки, но не поймёт
перефразированный вопрос.

**Шаг 3. Сливаем два списка в один.** Два поиска дали два рейтинга, и оценки
у них в разных шкалах — складывать их напрямую нельзя, как нельзя складывать
градусы с километрами. Поэтому используется приём **RRF** (Reciprocal Rank
Fusion): забываем про оценки, смотрим только на **места**. Кто стоял первым в
любом из списков, получает много баллов; кто восьмым — мало.

Аналогия: два эксперта составили свои топ-10 фильмов, но один ставит оценки от
1 до 5, другой от 0 до 100. Сравнивать оценки бессмысленно — сравниваем места.

**Шаг 4. Собираем «контекст».** Берём лучшие абзацы и складываем в текст,
который пойдёт модели. Тут два ограничения:

- *Бюджет в токенах.* Токен — это кусочек слова, примерно 3 символа русского
  текста. Модель не может читать бесконечно: у неё есть окно. У нас бюджет
  3200 токенов, максимум 8 абзацев.
- *Лучший абзац идёт первым.* Модели хуже видят середину длинного текста, чем
  начало и конец. Это известный эффект, называется *lost in the middle*.
  Аналогия: длинный список покупок — начало и конец помнишь, середину теряешь.

**Шаг 5. Модель пишет ответ.** Ей дают системную инструкцию («отвечай только
по этим абзацам, на каждое утверждение — ссылка на номер абзаца») и сами
абзацы.

**Шаг 6. Проверяем ответ у себя.** Модель обязана вернуть не свободный текст,
а структуру: текст ответа, список цитат, статус. Мы проверяем, что каждая
цитата **дословно** есть в том абзаце, на который модель ссылается.

Последний шаг — самый дешёвый детектор вранья из существующих. Не нужна ни
вторая модель, ни человек: подстрока либо есть в тексте, либо нет.

# Часть II. Зачем нужен «золотой набор»

## 4. Проблема, которую не видно

Ты открываешь чат, задаёшь пять вопросов, получаешь пять хороших ответов и
думаешь: работает. Это самая распространённая ошибка в таких проектах.

Пять вопросов — это не измерение, это впечатление. Ты неосознанно задаёшь те
вопросы, на которые система отвечает: формулируешь как автор документации,
спрашиваешь про то, что сам недавно читал. Вопросы живого сотрудника выглядят
иначе — со сленгом, опечатками, про то, чего в документах нет вообще.

## 5. Решение: экзамен с заранее известными ответами

**Золотой набор** — это список вопросов, для каждого из которых мы заранее
записали, каким должен быть правильный ответ. У нас их 77.

Каждый вопрос размечен так:

```json
{
  "id": "q041",
  "question": "сколько времени канарейка держится перед полной раскаткой",
  "type": "fact",
  "difficulty": "medium",
  "answerable": true,
  "docs": ["RL-423"],
  "must_contain": ["не менее суток"],
  "critical": false
}
```

Что здесь важно:

- **`docs`** — в каком документе лежит ответ. Размечено по *имени документа*,
  а не по номеру абзаца. Это принципиально: номера абзацев меняются при каждой
  переиндексации, а имя документа — нет. Разметка по номерам сломалась бы при
  первом же изменении настроек, и тогда это не эталон, а фотография одного
  прогона.
- **`must_contain`** — какая подстрока обязана попасть в найденный текст. Так
  мы проверяем, что найден не просто нужный документ, а нужный **абзац**.
- **`answerable`** — есть ли ответ в корпусе вообще. У нас 10 вопросов из 77
  (13%) — про то, чего в документах нет. Это не лень разметчика, а
  обязательная часть экзамена: без таких вопросов система не наказывается за
  привычку всегда что-нибудь отвечать. Аналогия: если на экзамене все вопросы
  имеют ответ, студент, который никогда не говорит «не знаю», получит пятёрку.
- **`critical`** — вопрос, ошибка в котором стоит дорого («можно ли выкладывать
  в пятницу» — можно уронить прод). Такие вопросы проверяются **поимённо**, без
  права на средние показатели.
- **`type`** — тип вопроса, и вот это самое полезное поле. Типы у нас такие:

  | тип | что проверяет |
  |---|---|
  | `fact` | простой факт из одного раздела |
  | `negation` | различается отрицанием с парным вопросом («как включить» / «как отключить») |
  | `exact_code` | точный артикул: `E-1042`, `РЛ-4.2.3` |
  | `procedure` | порядок действий |
  | `multi_doc` | ответ требует двух документов |
  | `version` | в корпусе есть устаревшая и действующая версия одного факта |
  | `unanswerable` | ответа в корпусе нет |

  Зачем разрезать: одна общая цифра «качество 70%» не подсказывает, что
  делать. А «на отрицаниях 67%, на всём остальном 95%» — это уже готовая
  гипотеза: система не видит «не», и чинить надо это.

## 6. Что такое «прогон» и почему сохраняется целиком

**Прогон** — это один проход по всем 77 вопросам с записью всего, что
получилось. Сохраняется не средняя цифра, а файл с настройками и результатом
по каждому вопросу.

Почему не средняя: среднее скрывает структуру. «Метрика не изменилась» может
означать «два вопроса починились, три сломались» — это не ноль изменений, это
пять изменений поведения, о которых надо знать. Наш отчёт поэтому всегда
печатает построчно: *починилось столько, сломалось столько*.

## 7. Метрики: что вообще меряется

Метрики строго разделены на два лагеря, и это не педантизм.

**Метрики поиска** отвечают на вопрос «нашли ли мы нужный текст»:

- `recall@5` — оказался ли нужный документ в первых пяти. Если нет, никакой
  промпт уже не поможет.
- `context_hit` — доехал ли нужный **абзац** до модели.
- `chunk_top1` — стоял ли нужный абзац на первом месте.
- `chunk_mrr` — усреднённая «насколько высоко он стоял».

**Метрики ответа** отвечают на вопрос «правильно ли модель этим
воспользовалась»:

- `status_ok` — правильный ли ярлык («ответил» / «не найдено»).
- `answer_contains` — есть ли в тексте ответа ключевой факт.
- `judge_ok` — что сказала модель-судья (об этом дальше).
- `цитат не прошло` — сколько цитат не нашлись дословно.

Зачем разделять: если считать одну общую цифру, то на вопрос «почему стало
хуже» ответа нет. Непонятно, поиск перестал находить или модель перестала
пользоваться найденным. А это два разных ремонта.

# Часть III. Первый замер и четыре дефекта

## 8. Первая цифра: 22%

```
recall@5      1.000    поиск находит нужный документ всегда
context_hit   1.000    нужный абзац доезжает до модели всегда
chunk_top1    0.895    и в 90% случаев стоит первым
status_ok     0.221    а правильно система отвечает в 22% случаев
```

Поиск идеален, ответы — нет. Значит проблема где-то после поиска.

## 9. Ловушка, в которую я почти попал

Дальше был такой разрез:

```
вопросы БЕЗ ответа в корпусе:  правильных отказов  1.000  (10 из 10)
```

Идеально! Система отказывается ровно там, где надо. Я перед прогоном сам
говорил, что это главная цифра.

Но вот вторая строка:

```
вопросы С ответом в корпусе:   ответов по существу  0.104  (7 из 67)
```

Из 67 вопросов, ответ на которые лежит в документах — и лежит в тексте,
который модель видела, — система отказалась отвечать на **60**.

**Аналогия.** Представь продавца в магазине, которого оценивают по одному
показателю: «как часто он честно говорит, что товара нет». Продавец, который
на любой вопрос отвечает «нет в наличии», получит по этому показателю ровное
100%. Он идеален по метрике и бесполезен в магазине.

> **Правило.** Любую метрику, которую можно выкрутить в максимум одним
> вырожденным поведением, нельзя показывать в одиночку. Рядом обязана стоять
> метрика, которую это поведение ломает. Точность рядом с полнотой. Доля
> отказов рядом с долей ответов. Скорость рядом с качеством.

Теперь отчёт печатает обе строки рядом и дописывает предупреждение, когда
видит такой перекос. Заодно это ответ на вопрос, зачем в наборе обязательные
10–15% вопросов без ответа: одна цифра без другой врёт.

## 10. Дефект №1: порядок полей в бланке

### Что такое «структурированный вывод»

Модель по природе выдаёт поток текста. Нам от неё нужна структура: текст
ответа отдельно, цитаты отдельно, ярлык «ответил / не нашёл» отдельно. Иначе
интерфейсу приходится угадывать регулярками, отказ это или ответ, — и всё
рассыпается при первой смене формулировки.

Способ получить структуру — **JSON Schema**: описание формы ответа, которое
отдаётся вместе с запросом.

```python
ANSWER_SCHEMA = {
    "properties": {
        "status": {"enum": ["answered", "not_found", "need_clarification"]},
        "answer": {"type": "string"},
        "citations": {...},
    },
    "required": ["status", "answer", "citations"],
}
```

**Аналогия:** это бланк. Не просьба «ответьте, пожалуйста, по форме», а
физический бланк с графами.

### Почему это именно бланк, а не просьба

Важная деталь: движок (у тебя llama.cpp внутри Ollama) превращает схему в
**грамматику** — набор жёстких правил, что вообще можно написать следующим
символом. На каждом шаге генерации запрещённые варианты просто вычёркиваются.

То есть модель **физически не может** написать поля в другом порядке или
пропустить графу. Бланк с металлическими рамками: вне поля ручка не пишет.

Отсюда первое неочевидное следствие: **порядок полей в схеме — это порядок, в
котором модель обязана их заполнять.** Не «желательный», а единственно
возможный.

### Почему порядок вообще что-то меняет

Вторая деталь: модель **авторегрессивна**. Значит каждое следующее слово она
выбирает, глядя на весь текст, который уже написан, включая то, что написала
сама секунду назад. У неё нет отдельного места, где она «сначала думает, а
потом пишет». **Письмо и есть думание.**

**Аналогия.** Человек, который думает вслух и слышит сам себя. Если первое, что
он произнёс, было «в общем, ничего не получится» — дальше он будет обосновывать
именно это, даже если факты говорят обратное. Не потому что упрямый, а потому
что уже сказанное стало частью того, из чего он исходит.

**Медицинская аналогия, ещё точнее.** Врач, у которого в карте графа
«заключение» стоит **перед** графой «осмотр». Он обязан заполнять по порядку:
написал «здоров», и дальше описывает осмотр так, чтобы не противоречить
собственному заключению. Поменяй графы местами — и тот же врач напишет
осмотр, а потом заключение по осмотру.

### Что у нас произошло

`status` стоял первой графой. Значит модель должна была вынести приговор
«есть ответ / нет ответа» **до того, как написала хоть одно слово ответа** —
без единого шага рассуждения.

А самая громкая инструкция в промпте была: «придуманный ответ хуже честного
„не найдено“». В условиях неопределённости модель выбирала осторожное
`not_found`. И с этого мгновения в её собственном контексте стояла строка
`"status": "not_found"` — после чего она писала текст **согласованно с уже
выданным ярлыком**.

Поэтому ущерб был двойной. Не только неправильный ярлык:

```
q003  статус: not_found
      ответ: «Отключение кэша на боевой установке запрещено. Подписчики
              рассчитывают на срез при подключении, без него интерфейсы
              показывают пустые табло, что операторы воспринимают как
              аварию связи.»
```

Ответ правильный, полный, с причиной — и помечен «не найдено». Но встречались
и такие:

```
q041  вопрос: сколько канарейка держится перед полной раскаткой
      в документе: «не менее суток»
      в ответе:   «...не менее одного рабочего дня, конкретное время
                   не уточняется»

q043  вопрос: что делать в первый день онбординга
      нужный абзац стоял ПЕРВЫМ в контексте
      в ответе:   «в документации не указано, что именно нужно делать»
```

Один почерк: «немного по теме, однако конкретного нет». Модель дописывала
текст под ярлык, который сама выдала пятью токенами ранее. **Ярлык впереди
содержания отравляет содержание.**

### Починка

```python
ANSWER_SCHEMA = {
    "properties": {
        "answer": {"type": "string"},   # сначала содержание
        "citations": {...},             # потом чем подкреплено
        "status": {"enum": [...]},      # и только теперь ярлык
        "clarifying_question": {"type": "string"},
    },
    "required": ["answer", "citations", "status"],
}
```

И в промпте прямо написано, чем `status` стал: не решением, принимаемым
заранее, а **пометкой о том, что уже написано**.

Бесплатный бонус: первый токен ответа приходит раньше, потому что модели больше
не надо сначала выписать `{"status":"answered","answer":"`.

> **Правило.** В структурированном выводе поле-ярлык (статус, категория,
> оценка, вердикт, «да/нет») ставится **после** поля-содержания. Ярлык — это
> вывод из рассуждения, а рассуждение в такой модели — это написанный текст.
>
> Если ярлык всё-таки нужен первым (бывает), то перед ним ставят поле для
> рассуждения: `reasoning`, `evidence`, `relevant_fragments`. Такое поле в
> схеме — не «болтовня для логов», а место, где модели **разрешено подумать**
> перед приговором.

### Результат

`status_ok` вырос с 0.221 до 0.987. Ответы по существу: с 7 из 67 до 67 из 67.
Починилось 52 вопроса, сломался 1 (о нём в разделе 12).

Одна строка в схеме.

## 11. Дефект №2: метрика мерила бумажку, а не больного

### Почему дефект №1 прожил так долго

У нас же была метрика качества ответа — почему она не орала раньше?

Потому что `status_ok` сравнивает **поле `status`** с ожидаемым. Это проверка
ярлыка, а не содержания. Она честно показала 10% — и показала бы ровно те же
10%, если бы модель вместо ответов писала стихи.

**Аналогия.** Оценивать здоровье пациента по тому, что написано в графе
«заключение», не глядя на пациента. Заключение — это метка. Пациент — это
факт.

А вторая метрика, `judge_ok`, стояла в отчёте как `0.000` — при том что судья
вообще не запускался. Отсутствие измерения превращалось в ноль, то есть в
«всё плохо».

### Починка 1: прочерк вместо нуля

`judge_ok` теперь `None` и печатается как `—`.

«Не мерили» и «всё забраковано» — разные новости. Ноль вместо пустоты — это
полдня, потраченные на починку беды, которой нет.

### Починка 2: самая дешёвая проверка правильности

Мы уже знаем, какой факт обязан быть в ответе — он лежит в разметке золотого
набора (`must_contain`). Значит можно просто проверить, есть ли он в тексте
ответа. Подстрокой. Без модели, без затрат, без калибровки.

```python
def answer_contains(answer, must_contain):
    haystack = " ".join(answer.split()).lower().replace("ё", "е")
    return all(needle in haystack for needle in must_contain)
```

Проверка **строгая в одну сторону**, и это надо понимать:

- `False` — **сильный** сигнал. Факта в ответе нет, ответ плохой, доказано.
- `True` — **слабый** сигнал. Факт упомянут, но вывод мог быть кривым
  («`TG_SNAPSHOT_CACHE=off` включает кэш» — подстрока на месте, смысл
  перевёрнут).

Поэтому она не заменяет судью, а задаёт ему **нижнюю границу**: если судья
поставит оценку выше, чем подстрока, значит судья хвалит ответы, в которых
нужного факта просто нет — и калибровать надо судью, а не систему.

Прогнал по сохранённому первому прогону:

```
ключевой факт есть в тексте ответа:  53 из 67  (79%)
статус «ответил»:                     7 из 67  (10%)
```

Вот цена дефекта №1: система знала ответ в четырёх случаях из пяти, а
признавалась в этом в одном из десяти.

### Починка 3: у дешёвой метрики тоже есть брак

После починки схемы осталось 10 провалов. Разобрал по одному — и **пять из
десяти оказались брёхом самой проверки**:

```
q007  в документе: «расчёт не заменяет осмотр»
      в ответе:    «труба не списывается по расчёту, решает осмотр»
      проверка искала «не заменяет» → не нашла → провал

q001  в документе: «TG_SNAPSHOT_CACHE=off»
      в ответе:    «...переменную TG_SNAPSHOT_CACHE на значение off»
      проверка искала «TG_SNAPSHOT_CACHE=off» → провал
```

Ответы верные. Врёт проверка.

**Аналогия.** Металлодетектор в аэропорту, который пищит на фольгу от
шоколадки. Он работает — но если половина его срабатываний ложные, охрана
перестаёт на него реагировать, и тогда он хуже, чем отсутствие детектора.

Причина ошибки не в подстроках, а в проектировании. Я разметил `must_contain`
**формулировкой документа** — и для его исходной задачи это правильно: поле
проверяет, доехал ли нужный текст, а текст в документе написан именно так.
Потом я тем же полем стал проверять **ответ**. А ответ — это пересказ. Он
законно передаёт «расчёт не заменяет осмотр» словами «труба не списывается по
расчёту».

**Аналогия.** Цитата из закона и пересказ юриста. Требовать от юриста
дословности кодекса — значит объявить врущими всех, кто объясняет понятно.

Развёл на два поля:

| поле | что проверяет | чьей формулировкой размечено |
|---|---|---|
| `must_contain` | нужный текст доехал до модели | документа |
| `answer_must_contain` | факт оказался в ответе | человека |

Второго нет — берётся первое. И внутри одной подстроки заработал `|`, то есть
«или»: один факт, разные слова.

```json
"must_contain": ["не заменяет"],
"answer_must_contain": ["не заменяет | не списывается | не является основанием", "осмотр"]
```

Список — это «и» (каждый факт обязан быть), внутри элемента — «или» (любая
формулировка годится).

> **Правило.** Дешёвая метрика тоже требует калибровки. Судью калибруют
> статистикой по размеченной выборке, подстроку — глазами по списку её
> собственных срабатываний. Пропустить этот шаг нельзя: метрика с 50% ложных
> тревог хуже отсутствия метрики, потому что ей верят.

Показательный момент: в разрезе по типам `negation` был худшим —
`answer_contains` 0.667. Не поправь я разметку, пошёл бы чинить отрицания,
которых не сломано. Четыре из пяти его провалов были брёхом.

После правки разметки: 0.925 вместо 0.851, и осталось ровно 5 настоящих
провалов.

## 12. Дефект №3: бланк без дна

### Сломавшийся вопрос

После починки схемы один вопрос стал хуже:

```
q068  «как мигрировать сервисы в Kubernetes»   (ответа в корпусе нет)
      статус: answered
      ответ:  «Сведений о процессе миграции сервисов в Kubernetes нет
               во фрагментах предоставленных документов.»
      цитат:  0
```

Модель **написала отказ** и пометила его «ответил». Зеркало дефекта №1: там
писала ответ и помечала «не найдено», здесь наоборот.

### Первая попытка починки — и почему она не сработала

Соблазн был снова править промпт. Это неправильный ход: мы уже видели, что
ярлык от модели ненадёжен в обе стороны, и третья формулировка правила дала бы
третий вид той же ошибки.

Правильный ход — проверить у себя. У нас есть железное правило: каждое
утверждение подкрепляется ссылкой на абзац. Значит «ответил, но сослаться не
на что» — **проверяемое противоречие**, и проверяется оно арифметикой:

```python
if status == "answered" and not citations:
    status = "not_found"
```

Прогнал — **ничего не изменилось**. q068 остался как был.

### Куда полез разбираться

Не в догадки, а в **трейс**. Трейс — это запись того, что происходило внутри
на каждом запросе: сколько времени заняло, сколько токенов, чем закончилась
генерация. Мы его пишем в файл на каждый вопрос, и именно для таких случаев.

```
q068  finish_reason:      length      ← вот оно
      completion_tokens:  700         ← ровно лимит
      ttft_ms:            594
      total_ms:           5317
```

`finish_reason: length` означает: модель не закончила сама, её **оборвали** по
лимиту. `num_predict = 700` — максимум токенов на ответ, и она в него
уперлась.

Дальше цепочка: поток оборвался на середине JSON → JSON не закрылся → разбор
провалился → управление ушло в ветку «не смогли разобрать» → а там стояло:

```python
status = ANSWERED if streamed_text.strip() else ERROR
```

То есть **до моей проверки дело вообще не дошло**. Я починил одну дорогу к
неправильному ярлыку, а их было две.

### Откуда 700 токенов на одно предложение

Ответ на q068 — одна фраза. Откуда 700 токенов?

Из схемы. Массив цитат не имел верхнего предела:

```python
"citations": {"type": "array", "items": {...}}
```

Грамматика, построенная из такой схемы, после каждого элемента массива
разрешает следующий. **Всегда.** У модели, которой цитировать нечего, нет
внутреннего «хватит» — и она набивала массив, пока не кончились токены.

**Аналогия.** Анкета, в которой графа «перечислите источники» не имеет числа
строк, а бумага не кончается — просто рулон. Добросовестный человек напишет
ноль строк и пойдёт дальше. Растерянный будет писать что-нибудь, пока рулон не
упрётся в конец.

Это второй случай ровно того же класса, что порядок полей:

> **Правило.** Схема структурированного вывода — не описание формата, а
> программа поведения модели. Любая повторяющаяся структура в ней обязана
> иметь верхнюю границу. Просьба в промпте («не больше четырёх цитат»)
> ограничивает вежливо, `maxItems` ограничивает **декодирование**. Разница
> видна ровно в тот момент, когда модель перестаёт слушаться.

### Три правки, одна болезнь

| правка | что делает | роль |
|---|---|---|
| `"maxItems": 4` в схеме | модели больше некуда лить | лечение причины |
| неразобранный JSON → статус `error`, а не `answered` | «ответил» значит «структура проверена» | страховка |
| пометка «обрезан по лимиту» ставится всегда | убирает слепое пятно в диагностике | страховка |

Третья — отдельная мелкая мерзость, которую стоит запомнить. В пайплайне
стояло:

```python
if finish_reason is LENGTH and status is ANSWERED:
    schema_error = "ответ обрезан по лимиту токенов"
```

Условие «только если статус answered» означало, что пометка про обрыв **не
ставилась именно при обрыве**: при обрыве JSON не закрывается, разбор падает, и
статус к этому моменту уже не `answered`. Проверка, которая не срабатывает в
своём главном случае, — не проверка.

## 13. Дефект №4: лабораторный журнал без графы «реактив»

Самое полезное в истории с q068 — не сам q068, а строка, которую напечатал
инструмент сравнения после второй попытки:

```
конфигурации совпадают — это замер разброса, а не сравнение изменений
```

### Что это значит

У нас есть команда `compare`: сравнить два прогона и сказать, чем они
различались и что изменилось в метриках. Логика простая и правильная:

- если настройки различаются одним параметром — можно приписать разницу ему;
- если ничем не различаются — значит это **замер разброса**, то есть измерение
  собственного шума системы;
- если различий несколько — прямо сказать, что результат приписать нечему.

«Замер разброса» — важная штука. Модель недетерминирована: один и тот же
вопрос может дать чуть разные ответы. Поэтому прежде чем радоваться «стало на
2% лучше», надо знать, на сколько процентов цифра гуляет **сама по себе**. Это
и есть порог значимости.

### В чём соврал инструмент

Формально он был прав: ни одно поле конфигурации не изменилось. Промпт тот же,
схема та же, порог, модель, top_k — всё то же. Изменился только один файл кода.

Фактически он соврал: сказал «система та же», хотя система была другая. И если
бы дельта оказалась ненулевой, я бы записал изменение поведения кода в
собственный шум системы — и отравил бы порог значимости для **всех** будущих
сравнений.

**Аналогия.** Лабораторный журнал, в который записывают температуру, давление
и время, но не записывают, что в середине серии сменили партию реактива.
Потом смотрят: «условия те же, а результат другой — значит это разброс
метода». И живут с завышенной оценкой погрешности годами.

Причина: снимок конфигурации описывал **настройки**. А система — это код плюс
настройки.

### Починка: отпечаток кода

`app/version.py` считает хэш от содержимого файлов, которые влияют на ответ
(пайплайн, провайдеры, RAG). Тесты и фронтенд не влияют и в отпечаток не
входят — иначе каждая правка теста давала бы ложное различие.

Теперь в сводке стоит:

```
модель qwen2.5:7b · эмбеддинги bge-m3 · промпт wiki-answer-1.0+6cfea59f · код 07056720c8f1
```

Любая правка кода видна как строка различий, а «конфигурации совпадают»
означает то, что должно означать. И отдельно: если у одного из прогонов
отпечатка нет (все прогоны до этого момента), `compare` печатает оговорку —
совпадение настроек там ничего не доказывает.

> **Правило.** В снимок конфигурации входит **всё**, что влияет на результат:
> модель, настройки, промпт, схема, разметка, код. То, чего в снимке нет,
> однажды изменится молча — и тогда метрика соврёт не в цифре, а в
> **объяснении**, почему цифра такая. Врущее объяснение дороже врущей цифры:
> по нему принимают решения о том, что чинить дальше.

## 16. Что дальше по плану шага 2

**Судья.** LLM-as-judge — отдельная модель, которая читает вопрос, эталонные
выдержки из документов и наш ответ, и говорит «верно / неверно». Нужна потому
что подстрока не видит перевёрнутого смысла. Запускается **вторым проходом**, по
уже сохранённым ответам: на одной видеокарте отвечающая модель и судья
одновременно не помещаются — мы это уже выясняли, когда llama-server упал с
ошибкой CUDA.

**Каппа.** Судья тоже врёт, и прежде чем ему верить, его надо проверить на
людях. Берём 30–40 ответов, размечаем руками, считаем **каппу Коэна** — меру
согласия, устроенную так, чтобы вычесть случайные совпадения. Ниже 0.6 — судья
шумит, и его цифру в отчёте надо считать украшением, а не измерением.

Полезная сверка: `judge_ok` не должен оказаться выше `answer_contains`. Если
судья хвалит ответы, в которых нужного факта нет, — калибровать надо судью.

**Шум.** Три прогона без единого изменения. Разброс между ними — и есть порог
значимости. Сейчас в сравнении стоит `0.000`, то есть формально «любое различие
значимо». Для дельты +0.766 это неважно, для будущих +0.03 — критично.

**Гейт.** Золотой набор как тест перед слиянием ветки. Допуск **обязан**
равняться измеренному шуму, а не круглому числу от руки. Критичные вопросы
проверяются поимённо, без допуска.

# Часть V. Как про это рассказывать

Пять готовых историй. Каждая — с цифрой, потому что история без цифры звучит
как теория из статьи.

**Про структурированный вывод.** «Порядок полей в JSON Schema — это порядок
рассуждения модели: провайдер строит из схемы грамматику, а декодирование
авторегрессивно. У нас поле статуса стояло первым — система отказалась
отвечать на 60 вопросов из 67, при том что нужный абзац в 90% случаев был
первым фрагментом в контексте. Перенесли статус после ответа. Правило:
поле-ярлык всегда после поля-содержания, либо перед ним ставится поле для
рассуждения».

**Про ограничения в схеме.** «Любая повторяющаяся структура в схеме обязана
иметь верхнюю границу. У нас массив цитат был неограничен — на вопросе, к
которому цитировать нечего, модель набивала его до упора в лимит токенов,
поток обрывался, JSON не закрывался. `maxItems` ограничивает декодирование,
просьба в промпте — нет».

**Про метрики.** «Метрику, которую можно выкрутить одним вырожденным
поведением, нельзя показывать в одиночку. Доля правильных отказов у нас была
1.000 — и получалась тем, что система отказывала всем. Теперь в отчёте обе
стороны стоят рядом. И отдельно: отсутствие измерения печатается прочерком, а
не нулём, иначе незапущенный судья читается как провал качества».

**Про дешёвые проверки.** «Перед тем как строить LLM-as-judge, мы поставили
проверку подстрокой: есть ли в ответе ключевой факт из разметки. Бесплатная,
детерминированная, строгая в одну сторону. Именно она показала, что модель
знала ответ в 79% случаев, а система признавала это в 10%. Но и её пришлось
калибровать: половина её провалов оказалась ложными тревогами, потому что
разметка была сделана формулировкой документа, а ответ — это пересказ.
Развели на два поля».

**Про воспроизводимость.** «Мы сохраняли снимок конфигурации на каждый прогон
— модель, порог, версию промпта. И обнаружили, что кода в снимке нет: после
правки одного файла инструмент сравнения сказал „конфигурации совпадают, это
замер разброса“. То есть изменение поведения кода записалось бы в собственный
шум системы и отравило порог значимости. Добавили отпечаток кода в конфиг».

# Словарик

| термин | человеческим языком |
|---|---|
| **RAG** | «сначала найди, потом отвечай только по найденному» |
| **эмбеддинг, вектор** | адрес текста в многомерном городе; близкие темы — близкие адреса |
| **чанк** | абзац или раздел документа, единица поиска |
| **токен** | кусочек слова, ~3 символа русского текста; модель считает всё в них |
| **контекст** | текст, который мы положили модели перед глазами |
| **BM25** | обычный поиск по словам, ловит точные артикулы |
| **RRF** | слияние двух рейтингов по местам, а не по оценкам |
| **structured output** | ответ по жёсткому бланку, а не свободным текстом |
| **JSON Schema** | описание этого бланка |
| **грамматика** | бланк с металлическими рамками: вне графы не напишешь |
| **авторегрессивность** | модель читает то, что сама написала секунду назад |
| **TTFT** | time to first token — через сколько появилась первая буква ответа |
| **finish_reason** | почему генерация кончилась: сама (`stop`) или оборвали (`length`) |
| **трейс** | запись того, что происходило внутри на одном запросе |
| **золотой набор** | экзамен с заранее известными правильными ответами |
| **прогон** | один проход по всему набору с записью всего результата |
| **recall@k** | попал ли нужный документ в первые k |
| **MRR** | усреднённая «насколько высоко стоял нужный результат» |
| **LLM-as-judge** | отдельная модель в роли проверяющего |
| **каппа Коэна** | мера согласия судьи с человеком, с вычетом случайных совпадений |
| **порог значимости / шум** | насколько цифра гуляет сама по себе без изменений |
| **гейт** | автопроверка перед слиянием ветки |
