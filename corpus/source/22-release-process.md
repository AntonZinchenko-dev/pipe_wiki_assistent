# Регламент релизов РЛ-7.1

## Ветвление

Основная ветка — `main`, она всегда в состоянии, пригодном для выкладки.
Работа ведётся в ветках от `main` с префиксом по типу задачи: `feat/`,
`fix/`, `chore/`, `docs/`. Долгоживущих ветвей разработки нет.

Слияние — только через пул-реквест, только `squash`. История `main` — линейная
последовательность осмысленных изменений, а не журнал промежуточных
сохранений.

## Требования к пул-реквесту

1. Зелёный CI. Для фронтендов это `npm run check` (типы, ESLint, steiger,
   тесты), для сервисов — `make check`.
2. Одно ревью с одобрением от участника своей группы. Для изменений в
   контрактах API — дополнительно ревью группы-потребителя.
3. Описание, из которого понятно, что изменилось и зачем. Ссылка на задачу.
4. Изменения в поведении — с тестом, воспроизводящим прежнее поведение как
   упавшее.

Пул-реквест без зелёного CI на ревью не берут. Это не про строгость, а про
то, что ревьюер не должен выполнять работу линтера.

## Окна выкладки

| Что                        | Когда                                        |
| -------------------------- | -------------------------------------------- |
| Обычный релиз              | Вторник и четверг, 10:00–12:00 по Екатеринбургу |
| Исправление аварии         | В любое время, по регламенту инцидентов      |
| Изменение контракта API    | Только вторник, с уведомлением потребителей за 3 рабочих дня |
| Изменение схемы данных     | Только вторник, с планом откатной миграции   |

Выкладка в пятницу запрещена, кроме исправления действующей аварии. Причина
прозаическая: в субботу и воскресенье дежурит один человек, и разбирать
последствия ему будет нечем.

## Постепенная раскатка

Заметные изменения раскатываются в три шага:

1. **Теневой режим.** Новый код работает параллельно старому, результат
   логируется, но пользователю не показывается. Длительность — не менее
   одного полного рабочего дня.
2. **Канарейка.** Новый код обслуживает 10 % трафика, метрики сравниваются со
   старым по отдельному дашборду. Длительность — не менее суток.
3. **Полная раскатка.** Только если на канарейке нет расхождений по метрикам
   ошибок, задержке и стоимости.

Пропустить шаги можно только для исправления действующей аварии, и это решение
принимает дежурный, а не автор изменения.

## Обязательное для отката

Каждый релиз должен быть откатываемым без выкладки нового кода. Практически
это означает: новая версия читает данные, записанные старой, и наоборот —
хотя бы в течение одного релизного цикла. Миграции схемы делаются в два
шага: сначала совместимая с обеими версиями, затем удаление старого поля
отдельным релизом не раньше следующего вторника.

Версии, для которых откат невозможен, помечаются в описании релиза явно, с
объяснением почему, и требуют одобрения руководителя эксплуатации до
выкладки.

## Что фиксируется в каждом релизе

- Версия кода — хеш коммита.
- Версия модели данных или контракта, если менялись.
- Версия шаблонов отчётов, если менялись.
- Кто выкладывал и когда.

Все четыре величины попадают в журнал релизов автоматически. Ручные записи в
журнал не принимаются: если релиз не попал в журнал, значит он выложен вне
регламента, и это разбирается как инцидент.
