# Постмортем 2026-05-06 — пустые табло на трёх установках

## Что произошло

6 мая 2026 года операторы трёх буровых установок сообщили, что табло
телеметрии пустое: значения не отображаются вообще. Операторы восприняли это
как потерю связи с установкой и начали действовать по инструкции обрыва
связи, включая остановку операции на одной из установок.

Связь при этом была в порядке, данные шли, и в архив писались корректно.
Пустым было только представление.

Степень назначена S1: остановка операции на боевой установке.

| ----------- | -------------------------------------------------------------------------- |
| 06:12       | Плановая выкладка TELEMETRY-GW 2.0.4 (вне окна, как исправление S3)        |
| 06:40       | Первое обращение оператора: «табло не заполняется»                         |
| 06:55       | Второе и третье обращение с других установок                               |
| 07:10       | Дежурный подтверждает: поток идёт, архив пишется, срез не отдаётся         |
| 07:25       | Операция на установке №14 остановлена решением супервайзера                |
| 07:40       | Найдена причина: `TG_SNAPSHOT_CACHE=off` в конфигурации боевого стенда     |
| 07:52       | Значение возвращено в `on`, процесс перезапущен                            |
| 08:05       | Табло заполнились, операция возобновлена                                   |

## Почему сработало именно так

За неделю до инцидента кэш последних значений отключали на боевом стенде для
отладки файлового источника — это допускается регламентом через окно
обслуживания. Значение `TG_SNAPSHOT_CACHE=off` осталось в конфигурации стенда
после отладки.

Выкладка 2.0.4 перезапустила процесс. Переменная читается только при старте,
поэтому до перезапуска отключение никак себя не проявляло: процесс работал с
кэшем, поднятым ещё при прошлом старте. Между внесением изменения и его
проявлением прошло восемь дней.

Подписчик, подключившийся посреди рейса, получал только поток изменений.
Медленные теги — `hole_depth`, `wob` — меняются раз в несколько минут, поэтому
табло оставалось пустым достаточно долго, чтобы это выглядело как авария
связи.

## Что мешало заметить раньше

Три вещи.

Первая: отключение кэша не оставляло следа в наблюдениях. В журналах не было
ни предупреждения при старте с отключённым кэшем, ни метрики «доля
подключений, получивших срез».

Вторая: конфигурация боевого стенда правилась вручную и не сверялась с
эталоном в репозитории. Расхождение существовало восемь дней и никем не
проверялось.

Третья: выкладка прошла вне окна как «исправление S3». Регламент допускает
выкладку вне окна только для действующей аварии, а S3 таковой не является.

## Что изменили

1. Предупреждение в журнал при старте процесса с отключённым кэшем, уровень
   `WARN`, с текстом причины и последствий. Срок — 7 мая, выполнено.
2. Метрика «доля подключений, получивших срез» и оповещение при её падении
   ниже 99 %. Срок — 13 мая, выполнено.
3. Сверка конфигурации боевого стенда с эталоном при каждой выкладке,
   расхождение блокирует выкладку. Срок — 27 мая, выполнено.
4. Запрет выкладки вне окна для степеней ниже S2 — техническая проверка в
   конвейере, а не договорённость. Срок — 3 июня, выполнено.
5. Отключение кэша в продакшене переведено из «через окно обслуживания» в
   «запрещено»; для отладки источника поднимается отдельный экземпляр шлюза.
   Срок — 20 мая, выполнено.
