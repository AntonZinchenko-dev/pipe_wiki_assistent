# Регламент инцидентов РЛ-9.2

## Что считается инцидентом

Инцидент — любое событие, из-за которого пользователь не может выполнить свою
работу, либо данные стали недостоверными, либо нарушен регламент доступов.

Недостоверные данные — тоже инцидент, и более тяжёлый, чем недоступность.
Недоступный сервис виден сразу, а недостоверное число уходит в отчёт
заказчику и обнаруживается через недели.

## Степени

| Степень | Признак                                                                   | Реакция          |
| ------- | ------------------------------------------------------------------------- | ---------------- |
| S1      | Боевой контур недоступен, либо данные недостоверны у всех пользователей     | Немедленно, круглосуточно |
| S2      | Часть функциональности недоступна, обходной путь есть                      | В рабочее время, до 4 часов |
| S3      | Единичные ошибки, работе не мешают                                         | В плановом порядке |
| S4      | Косметика и неудобства                                                     | В бэклог         |

Степень назначает дежурный. Автор обращения может её оспорить, но не изменить
самостоятельно.

## Пороги оповещения

Оповещение поднимается автоматически, без участия человека, по следующим
порогам:

| Метрика                                          | Порог внимания | Порог аварии |
| ------------------------------------------------ | -------------- | ------------ |
| Доля ошибок 5xx на боевом контуре                | 1 %            | 5 %          |
| Задержка ответа API, 95-й процентиль             | 1,5 с          | 4 с          |
| Доля поздних пакетов телеметрии (`TG-409`)       | 5 %            | 15 %         |
| Задержка доставки телеметрии, 95-й процентиль    | 800 мс         | 3 с          |
| Отставание расчётного воркера, минуты            | 15             | 60           |
| Выработка ресурса трубы по Майнеру               | 50 %           | 80 %         |
| Расход на внешние сервисы, от дневного бюджета   | 80 %           | 120 %        |

**Действующие пороги по усталости — 50 % внимание и 80 % авария.** Значения
1,59 млн циклов и 0,018 % из ранних постмортемов относятся к наблюдаемым
величинам на кампании, а не к порогам, и порогами не являются. Пороги,
указанные в постмортемах до 2026 года, недействительны: они пересматривались
дважды.

## Порядок действий

1. **Зафиксировать.** Обращение в сервис-деске создаётся всегда, даже если
   починили за минуту. Незафиксированный инцидент не существует, а значит и
   его причина не будет устранена.
2. **Остановить кровотечение.** Сначала вернуть работоспособность — откатом,
   отключением функции, переключением на резерв. Разбор причины после.
3. **Сообщить.** S1 и S2 — в канал дежурства немедленно, с текущим
   состоянием, а не с готовым выводом.
4. **Разобрать.** Постмортем обязателен для S1 и S2, срок — 5 рабочих дней.

Откат по регламенту релизов возможен без выкладки нового кода. Если откат
невозможен, это должно было быть помечено в описании релиза заранее.

## Постмортем

Постмортем без имён и без поиска виноватого. Разбирается система, а не
человек: если один сотрудник смог сломать боевой контур одним действием, это
свойство системы, а не свойство сотрудника.

Обязательные разделы: что произошло, хронология по минутам, почему сработало
именно так, что мешало заметить раньше, какие изменения вносим и с каким
сроком.

Пункт «что мешало заметить раньше» — главный. Инцидент, обнаруженный
пользователем раньше, чем оповещением, всегда содержит второй дефект:
отсутствующее наблюдение.

## Дежурство

Дежурит один человек в неделю, смена с вторника. Дежурный имеет право
откатывать релизы и отключать функциональность без согласования и обязан
делать это, не дожидаясь автора изменения.

Дежурный не занимается плановыми задачами. Это не льгота, а условие: человек,
у которого есть план на неделю, будет тянуть с откатом.
